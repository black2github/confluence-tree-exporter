# Выгрузка дерева страниц Confluence в Markdown (offline-поставка)

Автономный пакет для **закрытого контура без доступа в интернет**. Выгружает
дерево (или отдельную страницу) Confluence в набор `.md`-файлов с frontmatter,
сохраняя иерархию «файл рядом с папкой» и разрешая внутренние ссылки.

Все зависимости приложены готовыми колёсами (`wheels/`).

**Сверка версий между контурами.** При старте каждая утилита (выгрузка и
critic) печатает строку вида
`confluence-tree-exporter: версия 1.1.0, отпечаток исходников 507883e2`.
Номер поднимается при каждой сборке пакета; отпечаток считается автоматически
по составу всех исходников — **любое** изменение любого файла его меняет,
даже если номер поднять забыли. Одинаковая версия на внутреннем и внешнем
контуре = совпадают и номер, и отпечаток.

Важно понимать, что это не коммерческий продукт, а набор скриптов для создания подручного средства/инструмента.
В нем почти наверняка есть ошибки, но, скорее всего, не критичные (не тормозящие конвертацию). 
На что обратить особое внимание: 

- на случаи описания требований внутри макросов. Далеко не все из них полностью или корректно обрабатываются. 
Если в вашем сервисе именно такая ситуация - сообщайте,подумаем, что можно сделать в ограниченные сроки пилота.
- на информацию по разметке цветом, когда одна цветовая разметка вложена в другую (см. отчет migration-colors-report.md после конвертации с ключем --tasks).

## Требования на целевой машине

- **Windows x64**
- **Python 3.12 (x64)** — установлен и доступен как `py -3.12` или `python`.
- **Сетевой доступ к самому Confluence** (интернет не нужен, но до
сервера Confluence машина достучаться должна — иначе выгружать нечего).

## Установка

1. Распакуйте архив в любой каталог, например `C:\confluence-tree-exporter\`.
2. Запустите в **PowerShell** установку (создаст `.venv` и поставит зависимости из `wheels\`):
  ```
   install.bat
  ```
3. Настройте доступ к Confluence — скопируйте пример и заполните значения:
  ```
   copy .env.example .env
   notepad .env
  ```
   Обязательные поля: `CONFLUENCE_BASE_URL`, `CONFLUENCE_USER`, `CONFLUENCE_PASSWORD`.

## Запуск

### Выгрузка целого дерева

```
run-tree.bat <page_id> <service_code> <subdir> [source] [флаги]
```

- `page_id` — ID корневой страницы поддерева в Confluence.
- `service_code` — код сервиса (влияет на путь и на `doc_id` в frontmatter), например `CORP_CARDS`.
- `subdir` — подкаталог внутри вывода, например `лимиты`.
- `source` — необязательный тег источника (по умолчанию `DBOCORPESPLN`).

Пример:

```
run-tree.bat 291472147 CORP_CARDS лимиты --tasks --http --with-images
```

Результат появится в:

```
conf-requirements\<service-code>\<subdir>\...
```

(рядом с `.bat`-файлами; `<service-code>` — код в нижнем регистре, `_`→`-`).

### Выгрузка одной страницы (или нескольких по запятой)

```
run-page.bat <page_id[,page_id2,...]> <service_code> <subdir> [source] [флаги]
```

| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--http`                        | Прямой HTTP-доступ (как браузер), в обход REST API. Помогает, если REST API закрыт (**ситуация на внутреннем контуре на 07.2026**).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

| `--tasks`                       | Выгружать ВСЁ содержимое с разметкой **CriticMarkup** — цветные фрагменты оборачиваются в маркеры задач `{++ID: …++}`/`{--ID: …--}` (см. раздел ниже). Взаимоисключающий с `--all`. Дополнительно пишет `migration-manifest.yaml` и отчёт по цветам.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `--keep-history`                | Сохранять таблицу «История изменений» (по умолчанию она вырезается).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `--with-images`                 | Скачивать картинки/образы... в подкаталог `img/` рядом с `.md`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `--with-attachments`            | Скачать файлы на странице в подкаталог `files/` рядом с `.md`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `--with-index`                  | Генерировать навигационные `index.md` по папкам (для статических генераторов сайтов, используемых для GitLab и т.д.). Только для `run-tree.bat`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `--drop-strikethrough`          | Исключать зачёркнутый текст. В режимах approved/`--all` — любой; в режиме `--tasks` — **только чёрный** (применённый мусор ПРОМ): цветное зачёркнутое — удаление задачей, оно всегда сохраняется маркерами `{--ID: …--}`, иначе `reject-all` не смог бы восстановить ПРОМ-состав.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `--unapproved-jira <file.json>` | Список Jira ID **неутверждённых** задач (эмуляция похода в RAG): если джира из списка стоит в **первой по дате** записи «Истории изменений» и эта запись **чёрная** (страница создана этой задачей) — состав страницы считается неутверждённым (случай новой страницы, где всё «чёрное» с рождения). Цветные записи той же даты этому не мешают. Если задача из списка встречается в истории позже, первая запись цветная, у первой даты есть чёрная запись другой задачи или первая запись без даты при неясном порядке таблицы — страница **не замораживается** (с версии 1.9.1; раньше хватало любой чёрной строки, и давно введённая страница могла уйти целиком), а случай попадает в отчёт `migration-colors-report.md`, секция «Задача из списка … страница НЕ заморожена»: чёрные правки такой задачи остаются в тексте, их разбирают руками. Реакция по режиму: с `--tasks` весь чёрный контент оборачивается вставками `{++ID: …++}` (reject-all даст пустую страницу, apply примет состав целиком), задача попадает в манифест с `confidence: forced`, frontmatter `status: draft`; без `--all`/`--tasks` страница пропускается с предупреждением; с `--all` — контент полный, но `status: draft`. Формат файла: `["GBO-1", "DBOCORPESPLN-123456"]` или `{"unapproved_jira": [...]}`. Ограничение: fenced-код-блоки маркерами не помечаются (предупреждение в логе). Без ключа поведение не меняется. |
| `--check-prom`                  | Сторож «ПРОМ не потерян» (только вместе с `--tasks`, с версии 1.9.10). После разметки каждой страницы слова среза `reject-all` сверяются с чёрным текстом источника (чёрное и всё зачёркнутое), слова `apply` — со вставками. Расхождение означает, что фрагмент ушёл не в тот маркер: текст ПРОМ потерян, вставка не снята или вставка потеряна. Такая страница попадает в лог предупреждением и в отчёт `migration-colors-report.md`, секция «Инвариант ПРОМ нарушен», со списком слов; выгрузка не останавливается. Сравнение словарное (без порядка и пунктуации), расхождения только границ слов не считаются; нумерация списков «N. » и служебные теги экспортёра не считаются, а текстовые токены вида `<vpan>` и XML в блоках кода считаются как текст (с версии 1.9.11). С версии 1.9.13 из источника строятся те же два среза, что даёт критик: ПРОМ из чёрного и удалений, `apply` из чёрного и вставок. Номер «N. » в начале строки снимается в каждом срезе так же, как в markdown. Столбец источника с именем `status` считается текстом. Известные классы, которые сторож показывает намеренно: цветной текст внутри инлайн-кода, цветной фрагмент внутри текста ссылки, уплощение вложенных цветов по ТЗ п. 4.5. Намеренные обёртки чёрного (уплощение вложенности ТЗ п. 4.5) могут давать сигнал — это позиции того же ручного разбора; страницы с форс-обёрткой `--unapproved-jira` не проверяются. Стоит примерно столько же процессорного времени, сколько сама разметка; сеть не затрагивает. Без флага поведение не меняется. |




Пример с флагами:

```
run-tree.bat 291472147 CORP_CARDS лимиты --http --with-images --all
```

## Миграция статуса требований (CriticMarkup)

Помимо режимов «только подтверждённые» и `--all`, пакет умеет выгружать требования
с сохранением **статуса задач** в разметке CriticMarkup: цвет фрагмента (задача Jira из
таблицы «История изменений») превращается в маркер `{++ID: …++}` (добавлено), `{--ID: …--}`
(удалено) или служебный столбец `status` в таблицах.

Выгрузка с маркерами:

```
run-tree.bat 291472147 CORP_CARDS лимиты --tasks --http --with-images
```

Кроме `.md` с маркерами создаются:

- `migration-manifest.yaml` — реестр мигрировавших задач (с `first_seen` — датой первой записи истории);
- `migration-colors-report.md` / `.json` — отчет по цветам, включая те, что без задачи (`UNKNOWN-*`), коллизии,
уплощённые вложенности, сводка цветов с ΔE (для калибровки "черного") — вход для ручного разбора;
- `migration-apply-order.md` — предложение ПОРЯДКА вливания задач на внешнем контуре
(по дате первой записи «Истории изменений»; задачи одного дня помечены, задачи без
даты — отдельной секцией) + готовый блок команд `apply`.

В отчёте каждый цвет показан в двух формах: **«Цвет в HTML»** (`rgb(255,102,0)`) — та,
в которой он записан на странице Confluence, по ней фрагмент ищется поиском в исходнике;
и канонический `#rrggbb` — для сверки с набором `black_colors`. Уплощения делятся по
`confidence`: `high` (структурная вложенность цветов), `medium` (зачёркнутый фрагмент
вплотную к правке другой задачи — приоритетная очередь проверки), `post-pass`.
С версии 1.9.15 структурная вложенность уплощается и в HTML-таблицах (ячейки и пункты
списков внутри них), как в обычном тексте: фрагмент другой задачи внутри цветного
элемента больше не поглощается маркером внешней задачи.

Дальнейшая работа с маркерами — утилитой **critic** на внешнем контуре (работает с локальными `.md`, Confluence
не нужен):

```
run-critic.bat apply GBO-12345 --path conf-requirements\   REM принять правки задачи (вышла на ПРОМ)
run-critic.bat reject GBO-12345 --path conf-requirements\  REM откатить правки задачи
run-critic.bat apply-all --path conf-requirements\         REM целевое состояние (все задачи приняты)
run-critic.bat reject-all --path conf-requirements\        REM текущий ПРОМ (все правки убраны)
run-critic.bat lint --path conf-requirements\
run-critic.bat list --path conf-requirements\              REM список незавершённых задач
```

Команды правки редактируют `.md` **на месте** (модель работы под git: diff/ревью/откат).
С версии 1.9.15 пункт списка, целиком состоявший из снятой правки, удаляется вместе со
строкой (в HTML-таблицах — пустой `<li>` и опустевший из-за этого список); пустые пункты,
которые были в источнике без разметки, остаются.
Подробное руководство: `app\scripts\CI\critic_manual.md`.

**Сверка по архиву raw (с версии 1.9.14)** — `app\scripts\CI\raw_oracle.py`. Проверяет, что фрагмент,
который в архиве `sources/raw` стоит под маркером удаления введённой задачи (тег `src/<ID>` с HEAD
репозитория), не остался дословно в применённой копии той же страницы в `sources/confluence` —
снятие доведено. Разбор маркеров — функциями critic (все три нотации: `{--…--}`, старая часть
`{~~…~>…~~}`, HTML `critic-del`/`critic-row-del`, строки таблиц со столбцом `status = -ID`).
Два режима:

- **копии** — вызывает прибор самопроверки канона анализа: `selfcheck.py --raw <sources/raw>
  --bundle <каталог этой поставки>` (на машине, где вводят задачи `run-history.bat`). Результат —
  строки ⚠ с файлом и строкой копии, вердикт selfcheck не меняется; ячейки вложенных таблиц
  HTML-островов по умолчанию пропускаются (ключ selfcheck `--include-nested-cells`);
- **карточки** — отдельный отчёт: тот же фрагмент дословно остался в карточке `docs/`, в
  `confluence_page_ids` которой стоит страница (недоснятие после ввода задачи — дозаход):

  ```
  .venv\Scripts\python -m app.scripts.CI.raw_oracle --cards <src>\docs --raw <src>\sources\raw --out отчёт.md
  ```

  Введённые задачи — теги `src/*` репозитория (как у `run-history.bat`) либо `--introduced <файл>`.
  Вложенные ячейки проверяются (`--skip-nested-cells` — пропуск). Совпадение в разделах карточки
  «Происхождение», «Долги и открытые вопросы», «Открытые вопросы», «Что не переносится из
  источника», «Изображения источника», «Источники миграции», «Долги по ссылкам» и в строках
  долга / `OQ-NNN` сигналом не считается; короткие фрагменты помечены «проверить».

  С версии 1.9.16 у отчёта два раздела. Второй — **вставки невведённых задач**: фрагмент, который
  в архиве стоит под маркером вставки задачи без тега `src/*` (все нотации: `{++…++}`, новая часть
  `{~~…~>…~~}`, HTML `critic-ins`/`critic-row-ins`, строки таблиц со столбцом `status = +ID`), в
  карточке встречается чаще, чем в срезе «как должен быть» (архив без удалений введённых и без
  вставок невведённых задач) и чем в применённой копии страницы — содержимое невведённой задачи
  попало в карточку. Применённые копии — `--applied <каталог>`, по умолчанию `<raw>\..\confluence`;
  без копии сверка только по архиву. Находки — тремя таблицами: основной список (к исполнителю),
  «проверить» (короткие), покрытые долгом (задача и ID карточки в одной строке
  `docs\traceability-matrix.md`; долг без ID карточки не покрывает). Столбец «регистрация» —
  есть ли задача в `sandbox\confluence-unapproved-jira-pages.md` и строка матрицы. Раздел
  дополняет ревью, а не заменяет: часть фрагмента, переложенная строка таблицы и короткие
  вставки в него не попадают.

Сравнение — после одинаковой нормализации обеих сторон: сняты HTML-теги, разметка markdown
(`**`, `__`, `` ` ``), маркеры CriticMarkup и значения `±ID` столбца status; ссылка — её текст;
сущности `&lt;`/`&gt;`/`&amp;` раскрыты; кавычки «»“”„ сведены к прямым, «ё» — к «е»; пробелы
схлопнуты, регистр не учитывается. Короткий фрагмент (4 слова или меньше 30 символов) в
отчёте по карточкам помечен «проверить»: общая фраза может совпасть случайно.

Не проверяет: задачи без тега (их удаления в копии и должны быть); фрагменты короче 4 слов или
20 символов; маркеры в блоках кода; текст, который введённая задача вставила заново.

**Ввод задач в ПРОМ и хронология (этапы 3–4 роадмапа)** — `run-history.bat`.
Репозиторий `src-<сервис>` ведётся как цепочка событий двух видов: «задача» и
«выгрузка». Утилита держит рабочее дерево «архив + введённые ранее задачи» вне
репозитория и на каждую задачу из файла делает: `apply` задачи в это дерево
(один раз) → копия дерева в `sources/confluence` без служебных файлов
`migration-*` → `reject-all` → `git commit` + `git tag <префикс><JIRA-ID>`.
Введённые ранее задачи утилита берёт сама из тегов, достижимых с текущей ветки;
в файле перечисляют только вводимые (уже введённые пропускаются с предупреждением).

```
run-history.bat <каталог-архива> <корень-git-репозитория> [<файл-списка-задач>] [опции]
```

Три применения:

- **Этап 3, чистый ПРОМ** — без файла задач на ветке `master`: целевого
  каталога ещё нет, утилита собирает его из архива и делает коммит
  «ПРОМ-срез: …».

  ```
  run-history.bat C:\src-cc\sources\raw C:\src-cc --base-dir C:\src-work
  ```

- **Ввод задачи в ПРОМ** — на `master`, в файле только вводимые задачи
  (по одной в строке), коммит «Ввод в эксплуатацию: …» + тег `src/<JIRA-ID>`.
  Сначала `--dry-run`: он показывает введённые ранее, план и ошибки проверок.

  ```
  run-history.bat C:\src-cc\sources\raw C:\src-cc intro.txt --base-dir C:\src-work --dry-run
  run-history.bat C:\src-cc\sources\raw C:\src-cc intro.txt --base-dir C:\src-work
  ```

- **Хронология на ветке `future`** — все задачи отчёта выгрузки по порядку,
  список — сам файл `migration-apply-order.md` из архива (подходит как есть),
  теги `hist/<JIRA-ID>`:

  ```
  run-history.bat C:\src-cc\sources\raw C:\src-cc C:\src-cc\sources\raw\migration-apply-order.md --tag-prefix hist/ --commit-prefix "Срез хронологии" --base-dir C:\src-work
  ```

**Новая выгрузка.** Архив кладут в `sources/raw` целиком (после очистки
каталога) и коммитят; затем запуск утилиты: если «архив + введённые ранее»
отличается от вершины ветки, она сначала фиксирует коммит «Выгрузка: …» без
тега и только потом режет новые задачи. На `master` запуск без файла задач
делает только это. Старые теги не перестраиваются.

В конце утилита печатает хвост «не введено N из M» по манифесту архива
(`migration-manifest.yaml`); пустой ввод (задача не изменила файлы) получает
коммит и тег с причиной — обычно её страницы целиком под флагом ещё не
введённой задачи.

Требования: git настроен (user.name/email), рабочее дерево чистое, HEAD на
ветке. Предохранители — остановка без порчи истории: грязное дерево, тег вне
ветки, недопустимое имя тега, задача вне манифеста архива (обход
`--allow-unlisted`), целевой каталог вне репозитория или внутри `.git`, новые
файлы среза под `.gitignore`, ошибка critic/git (целевой каталог возвращается
к HEAD, повтор продолжает с места останова). Push — только с явным `--push`
(ветка и теги этого прогона).
`--base-dir` — каталог для рабочего дерева между срезами (по умолчанию `%TEMP%`);
укажите каталог вне репозитория, вне архива и вне проверки антивируса, иначе
**каждая** итерация проходит через сканирование. `--refill-each` — прежний
способ (пересборка из архива на каждую задачу, в разы медленнее; результат тот
же, проверено побайтно на 148 срезах) — оставлен для сверки.
Полный список опций — в шапке `run-history.bat`.

## Починка уже выгруженных деревьев

Правки экспортёра действуют начиная с ОЧЕРЕДНОЙ выгрузки — деревья, выгруженные
раньше, остаются как есть. `run-repair.bat` лечит их на месте: доступ к Confluence
не нужен, поэтому чинить можно и во внутреннем контуре сразу после выгрузки, и во
внешнем после переноса файлов. Все починки идемпотентны — повторный запуск ничего
не портит.

```
run-repair.bat conf-requirements\ --unfold --flatten-nested --unfence-html --name-status-column --dry-run
run-repair.bat conf-requirements\ --unfold --flatten-nested --unfence-html --name-status-column
```

Сначала `--dry-run` и просмотр списка, затем тот же запуск без него. Это же
сочетание ключей — рецепт для выгрузок, снятых предыдущими версиями пакета:
после него `reject-all` снимает всю неутверждённую разметку за один заход.


| Ключ                            | Что чинит                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--unfold`                      | Свёрнутые значения frontmatter. PyYAML переносил длинное значение на вторую строку (для кириллицы это ~150 байт), и всё, что читает файл построчно — `grep`, инвентаризация выгрузки, — видело обрезанный `title` с незакрытой кавычкой; разные страницы выглядели дублями.                                                                                                                                                                                                                                                                                                                                                                                        |
| `--flatten-nested`              | Литеральную вложенность маркеров: `{++A: … {++B: …++} …++}`. Возникает, когда блочный маркер накрывает участок с врезками соседних задач. Нотация вложенность запрещает, поэтому `apply`/`reject` на таком файле падают с «литеральная вложенность маркеров запрещена» и обрывают весь прогон. Уплощение выносит внутренние маркеры наружу, текст внешнего остаётся за его задачей.                                                                                                                                                                                                                                                                                |
| `--unfence-html`                | Ограждения кода ``` внутри HTML-таблиц: заменяет их на `<pre>`. Как код такое не отображается нигде, а `apply`/`reject` считают всё между ограждениями кодом и переносят байт-в-байт — поэтому маркеры внутри они не видят, и неутверждённые требования молча остаются в «чистом ПРОМ». Для примера: на дереве сервиса "Корпоративные карты" из 614 страниц так пряталось 204 фрагмента разметки в 8 файлах (риск получить в ПРОМ-срезе фрагменты примеров запросов/ответов, не имеющих к нему отношения. Не фатально, но неприятно.) Меняются только ограничители, содержимое остаётся как было; если ограждения в таблице не сходятся в пары, файл не трогается. |
| `--name-status-column`          | Даёт имя служебному столбцу `status` в таблицах, где он остался безымянным. Нотация опознаёт табличную правку по имени столбца, а выгрузка Confluence держит заголовки внутри `<tbody>` — столбец оставался пустым, и `apply`/`reject` пропускали такую таблицу целиком: разметка `+JIRA-ID` доезжала до ПРОМ-среза, а строки, помеченные на удаление, не удалялись. Пустая ячейка шапки получает имя; если размечена сама шапка — над ней добавляется строка-шапка, маркер не теряется. Ячейку шапки, занятую текстом, не трогает. |
| `--flag-page <JIRA-ID>`         | Ставит страничный флаг `unapproved_jira` на ВСЕ страницы указанного пути. Для замороженного поддерева: требования не отменены, а отложены — в git они лежат целиком, но в ПРОМ-срез не попадают, а `apply <JIRA-ID>` возвращает их разом. Ключ `--unapproved-jira` здесь бессилен: он берёт задачу из маркеров в теле, а у таких страниц маркеров нет вовсе (нет таблицы «История изменений» → нет карты «цвет → задача», весь текст считается чёрным). Страница с флагом другой задачи не перезаписывается. Задача обязана встречаться маркером в обрабатываемом пути либо быть в `migration-manifest.yaml` — иначе прогон откажется работать: флага задачи, которой нет в дереве, не видит `critic list`, и страница осталась бы пустой навсегда. |
| `--unapproved-jira <file.json>` | Проставляет страничный флаг `unapproved_jira` там, где весь состав страницы принадлежит неутверждённой задаче (формат списка — как у `--unapproved-jira` в `run-tree.bat`). После этого `reject` очищает такую страницу целиком, включая блоки кода из макросов, которые маркерами не помечаются.                                                                                                                                                                                                                                                                                                                                                                  |


Обратите внимание: путь задаётся как каталог, и корневая страница поддерева — файл РЯДОМ с каталогом, а не внутри него. Её нужно указать отдельным запуском:

```
run-repair.bat <папка-поддерева> --flag-page GBO-52119
run-repair.bat <страница-поддерева>.md --flag-page GBO-52119
```

Безопасность: после каждой правки frontmatter сверяется по смыслу (`yaml.safe_load`
до и после), а уплощение — по тексту без разметки. Если правка изменила бы данные,
файл не пишется, а строка уходит в отчёт. Несходящаяся разметка (незакрытый маркер,
лишний закрыватель) не трогается — такие места показывает `run-critic.bat lint`.

Найти места, требующие починки, до её запуска:

```
run-critic.bat lint --path conf-requirements\
```

Линтер перечислит все случаи вложенности сразу — в отличие от `apply`/`reject`,
которые останавливаются на первом же файле.

С версии 1.9.6 границы fenced-блоков определяются по виду и длине ограждения (как в
GitLab): ```` ``` ```` внутри ````` ```` ````` — содержимое блока. Линтер показывает и блоки,
не закрытые по правилам GitLab: `W4` (предупреждение) — блок закрыт строкой с текстом после
кавычек (```` ```text ```` вместо ```` ``` ````); `E10` (ошибка) — блок не закрыт до конца
файла, и маркеры в хвосте `apply`/`reject` не обработают. Частый случай `E10` — закрывающие
кавычки приклеены к маркеру (`++}```` ``` ````): перенесите ```` ``` ```` на отдельную строку.

## Сверка флагов заморозки старой выгрузки

До версии 1.9.1 экспорт с ключом `--unapproved-jira` замораживал страницу целиком
(`unapproved_jira: <ID>` в frontmatter), если задача из списка стояла в **любой**
чёрной строке «Истории изменений». Если такая задача встречалась в середине истории
давно введённой страницы, страница тоже замораживалась, и `reject-all` оставлял от неё
один frontmatter. С версии 1.9.1 страница замораживается, только если задача из списка
стоит в первой по дате записи истории, то есть создала страницу.

Выгрузки, сделанные раньше, нужно проверить. Истории изменений в выгруженных файлах
нет, поэтому `run-audit.bat` читает её из Confluence заново по `confluence_page_id`
каждой страницы с флагом. Файлы выгрузки утилита **не меняет**. Запускается там, где
есть доступ к Confluence:

```
run-audit.bat conf-requirements\ --out audit.md
```

Последняя строка вывода показывает итог, например:

```
[audit] страниц с флагом: 216; ЗАМОРОЖЕНА ОШИБОЧНО: 3; нет данных: 0; флаг не по списку: 29; подтверждён: 184
```

| Вердикт | Что означает | Что делать |
|---|---|---|
| `ЗАМОРОЖЕНА ОШИБОЧНО` | Задача флага есть в истории, но страницу создала не она. После `reject-all` страница пуста | Выгрузить эти страницы заново версией 1.9.1 или новее (`run-page.bat <page_id> …` с теми же ключами, что при первой выгрузке) и заменить файлы |
| `нет данных` | В файле нет `confluence_page_id`, страница не открылась или история на ней не опознана | Открыть страницу в Confluence и проверить руками |
| `флаг не по списку` | Задачи флага в чёрных строках истории нет: флаг поставлен автоматически (вся страница под цветом одной задачи), ключом `--flag-page` или руками | Ничего: исправление таких страниц не касается |
| `подтверждён` | Задача флага создала страницу | Ничего |

Страницы с вердиктом `ЗАМОРОЖЕНА ОШИБОЧНО` перечислены в консоли и в первом разделе
отчёта `audit.md` с идентификаторами `page_id`. Код возврата: `0`, если таких страниц
нет, и `1`, если есть.

Сверяется история в её **текущем** виде. Если страницу правили после выгрузки, вердикт
относится к текущему состоянию.

## Выборка страниц по идентификаторам

`run-pick.bat` забирает из каталога выгрузки страницы с заданными идентификаторами.
У него два сценария, команда одна и та же; сценарий определяется тем, что лежит в
каталоге назначения.

**Извлечение в отдельный каталог.** Каталога назначения нет либо он пуст. Страницы из
списка складываются туда в той же структуре подкаталогов, что в выгрузке, вместе со
своими картинками. Каталог создаётся сам. Исходная выгрузка не меняется.

```
run-pick.bat conf-requirements\<service_code>\<subdir> C:\выборка --pages ids.txt
```

Файл `ids.txt` — список идентификаторов страниц: по одному в строке либо через пробел
или запятую; строки с `#` — комментарии. Идентификатор страницы — число из поля
`confluence_page_id` в начале её файла.

Последняя строка вывода показывает итог:

```
[pick] выполнено (извлечение в отдельный каталог); в списке: 4; заменена: 0; добавлена: 4; перемещена: 0; без изменений: 0; картинок: 14; ошибок: 0; предупреждений: 0
```

Если хотя бы одного идентификатора из списка в выгрузке нет, не создаётся ничего, а
отсутствующие перечислены строками с `✗`. Чтобы посмотреть итог, ничего не создавая,
добавьте `--dry-run`.

**Замена страниц в существующей выгрузке.** Каталог назначения уже содержит выгрузку.
Этот сценарий описан в следующем разделе.

## Перевыгрузка отдельных страниц

Если часть страниц старой выгрузки нужно заменить (например, страницы с вердиктом
`ЗАМОРОЖЕНА ОШИБОЧНО` из сверки выше или страницы со смешанным зачёркиванием,
исправленным в версиях 1.9.2–1.9.3), выгружать их поодиночке через `run-page.bat`
не стоит: страница ляжет в корень, вне структуры дерева, и её ссылки на соседние
страницы не разрешатся. Порядок другой: полная выгрузка во временный каталог, затем
перенос только нужных страниц.

1. Выгрузить дерево заново **теми же ключами**, что в первый раз, но в другой
   подкаталог (третий параметр), чтобы старая выгрузка осталась на месте:

   ```
   run-tree.bat <page_id> <service_code> <subdir>-new [те же флаги, что при первой выгрузке]
   ```

2. Составить файл со списком идентификаторов страниц, например `ids.txt`: по одному
   в строке либо через пробел или запятую; строки с `#` — комментарии. Идентификатор
   страницы — число из поля `confluence_page_id` в начале её файла, оно же в отчёте
   `run-audit.bat`.

3. Посмотреть план, ничего не меняя:

   ```
   run-pick.bat conf-requirements\<service_code>\<subdir>-new conf-requirements\<service_code>\<subdir> --pages ids.txt --dry-run
   ```

   Последняя строка вывода показывает итог, например:

   ```
   [pick] пробный прогон; в списке: 12; заменена: 11; добавлена: 0; перемещена: 1; без изменений: 0; картинок: 3; ошибок: 0; предупреждений: 0
   ```

4. Если в итоге `ошибок: 0`, выполнить перенос той же командой без `--dry-run`.
   Чтобы сохранить отчёт, добавить `--out pick.md`.

Оба каталога должны быть **одного уровня дерева**: относительный путь страницы от
каждого из них обязан совпадать. Если указать каталоги разного уровня, утилита
остановится с сообщением «каталоги не совмещены» и покажет пример расхождения.

| Итог по странице | Что произошло |
|---|---|
| `заменена` | Файл в старой выгрузке заменён файлом из новой, байт в байт |
| `добавлена` | Страницы в старой выгрузке не было, файл создан |
| `перемещена` | Страница в Confluence переименована или перенесена: файл записан по новому пути, файл по старому пути удалён |
| `без изменений` | Файлы совпадают, ничего не записано |

Для страниц с итогом `заменена` отчёт (`--out`) и последняя строка вывода называют причину:

| Причина | Что это значит | Что делать |
|---|---|---|
| `только разметка маркеров` | Текст страницы тот же, изменились только маркеры: вид, наличие или нотация | Результат исправлений экспортёра; переносить |
| `изменён текст` | Текст между маркерами отличается: страницу правили в Confluence после прошлой выгрузки | Переносить как обычную новую выгрузку; в хронологии это событие «выгрузка» |
| `только страничный флаг` | Изменилась только строка `unapproved_jira` во frontmatter | Следствие правила страничной заморозки (версия 1.9.1) |
| `дополнен текст` | Старый текст сохранился целиком, добавились строки, пункты или абзацы; ничего не удалено и не переписано (с версии 1.9.12) | При первой выгрузке версией 1.9.11 и новее поверх более старой это восстановление текста, который экспортёр раньше терял, а не правка аналитика. Признак механический: правка в Confluence, которая только дописала текст, выглядит так же; при сомнении сверить с историей страницы |

Первая выгрузка версией 1.9.11 и новее поверх выгрузки 1.9.10 и раньше. Экспортёр
до 1.9.11 терял строки таблиц за пределами первого `<tbody>`, в `<tfoot>` и за
обёрткой внутри таблицы и терял список, вложенный прямо в список без пункта-обёртки.
Такие страницы получат причину `дополнен текст`. Исключение: экспортёр до 1.9.11 ставил
шапку вложенной таблицы после тела, теперь ставит первой. Это перестановка, а не
дописывание, и такая страница получит `изменён текст`, хотя в Confluence её не правили.
Таких страниц единицы: в архивах КК и Цифрового рубля по две, в lk-mp четыре.

Вместе со страницей переносятся картинки, на которые она ссылается (`img\…`).
Страницы не из списка, служебные файлы `migration-*` и картинки соседних страниц
утилита не трогает.

**Всё или ничего.** Если хотя бы одна страница из списка не найдена в новой выгрузке
или её целевой путь занят другой страницей, не записывается ничего, код возврата `1`,
причины перечислены строками с `✗`. Страница может отсутствовать в новой выгрузке,
если её удалили в Confluence, она попала под правила исключения или осталась без
собственного текста. Такой идентификатор нужно убрать из списка осознанно.

**Предупреждения** (строки с `⚠`) перенос не останавливают, но их нужно прочитать:
- ссылка новой страницы ведёт на файл, которого нет в старой выгрузке: соседнюю
  страницу переименовали в Confluence, её тоже стоит добавить в список;
- на старый путь перемещённой страницы ссылаются страницы, которые не
  перевыгружаются: их ссылки станут битыми, эти страницы тоже стоит добавить.

Перенесённые страницы несут **текущее** содержание Confluence, а не состояние на дату
первой выгрузки. После переноса проверьте разметку: `run-critic.bat lint --path …`.

## Возможные проблемы

- **Ошибка сертификата / не проходит коннект.** Если Confluence за самоподписанным
сертификатом (ситуация на 07.2026), откройте `app\confluence_loader.py` и замените `verify_ssl=True`
на `verify_ssl=False`.
- **REST API закрыт.** Добавьте флаг `--http` (или `CONFLUENCE_USE_HTTP=true` в `.env`).
- `install.bat` **не находит Python.** Проверьте `py -3.12 --version`. Нужен именно
Python 3.12 x64 (колёса собраны под эту версию и платформу).
